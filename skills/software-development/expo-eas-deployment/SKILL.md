# Expo EAS deployment

Use when deploying an Expo/React Native app to the Google Play Store or Apple App Store, or when the user asks how to install on Android/iOS devices, create a dev build, or submit to app stores.

## Always-on rules

- Prefer EAS cloud builds over local native toolchains unless the user explicitly asks for local builds.
- On Windows, local iOS builds are impossible; use EAS cloud for iOS.
- When the project uses native modules (expo-notifications, expo-image-picker, expo-document-picker, etc.), Expo Go is insufficient — install `expo-dev-client` and use a development build.
- Always use `npx expo install <package>` instead of `npm add` or `yarn add` — it resolves SDK-compatible versions.
- Always use `npx eas-cli <command>` or `npx eas <command>` instead of a globally installed `eas` binary.
- Never create or edit `ios/` or `android/` directories by hand; they are generated by CNG.

## Procedure

### 1. Inspect project state

Check these in order:

- `package.json`: SDK version, whether `expo-dev-client` is in dependencies.
- `app.json`: confirm `expo.slug`, `ios.bundleIdentifier`, `android.package`.
- `eas.json`: if missing, EAS has not been initialized.
- Lockfile: `package-lock.json` → npm; `bun.lockb` → bun; `yarn.lock` → yarn.

If `package-lock.json` is present, use npm commands; do not switch to bun or yarn.

### 2. One-time setup

Run in the project root:

```bash
npx expo install expo-dev-client
npx eas-cli login
npx eas-cli init
```

`eas init` creates `eas.json` and links the project to an EAS project, filling `extra.eas.projectId` in `app.json`. If `eas init` skips project setup, any build command will prompt through it.

### 3. Development builds (install on a device for testing)

For testing on a physical device or emulator before store submission:

```bash
npx eas-cli build --platform android --profile development
npx eas-cli build --platform ios --profile development
```

On Windows, do not attempt local iOS builds — use the EAS cloud command above. EAS returns a download URL for the installable binary when the build finishes.

After installing the dev build, start the JS server with `npx expo start` and connect from the app's launcher UI.

### 4. Production builds (store-ready binaries)

Ensure `eas.json` has a `production` profile:

```json
{
  "build": {
    "production": {}
  }
}
```

Then build:

```bash
npx eas-cli build --platform all
```

Outputs:
- Android → `.aab` for Google Play
- iOS → `.ipa` for App Store Connect

### 5. Submit to app stores

```bash
# Android (Google Play internal/alpha/beta/production)
npx eas-cli submit --platform android --latest

# iOS (App Store Connect → TestFlight)
npx eas-cli submit --platform ios --latest
```

Both upload the most recent build for that platform. Store listings must be created in Google Play Console and App Store Connect before submission.

### 6. Push JS-only bug fixes without rebuilding (EAS Update)

```bash
npx eas-cli update --branch production --message "Fix description"
```

This pushes a JS bundle update directly to installed apps. Use only for non-native changes.

## Pitfalls

- **Missing `expo-dev-client` + native modules = Expo Go crash.** Projects using `expo-notifications`, `expo-image-picker`, `expo-document-picker`, or any library with native code require a development build. Install `expo-dev-client` before building.
- **Windows cannot build iOS locally.** `npx expo run:ios` requires Xcode and only works on macOS. Use `eas build --platform ios --profile development` instead.
- **`eas.json` missing → EAS not initialized.** `eas init` must be run before any build command. If it fails, running a build command will walk through interactive project setup.
- **Store submission requires pre-created listings.** `eas submit` fails if the app does not already exist in Google Play Console or App Store Connect. Create the app listing first.
- **EAS Update is JS-only.** Changes to native code, `app.json`, or dependencies still require a full rebuild.
- **`app.json` `extra.eas.projectId` empty → project not linked.** Fill it via `eas init` or by running any `eas build` command.
- **`npx expo install` resolves SDK-compatible versions.** `npm install` or `yarn add` can pull incompatible versions; always use the Expo-managed installer.
- **Git root mismatch → EAS cannot find package.json.** If the git root is a parent directory of the project, EAS fails with "package.json is outside of the current git repository". Fix: run EAS from the project root, or pass `--workflowdir .`.
- **npm ci fails when lockfile is out of sync.** `npm ci` requires an exact match between package.json and package-lock.json. If missing or corrupted packages are reported, run `npm install` to regenerate, then `git add package-lock.json && git commit`. Do not switch to npm install in EAS unless you also adjust the workflow.
- **Corrupted `@file:` local deps in package-lock.json break npm ci.** Entries like `@file:emnapi/core` appear when the lockfile references local paths that no longer exist. Fix by deleting package-lock.json and node_modules, then running `npm install` to regenerate a clean lockfile.
- **Blank screen on native build = missing env vars at import time.** If the app's entry module (e.g., a Supabase client) throws when `EXPO_PUBLIC_*` variables are missing, the JS bundle crashes before rendering. EAS does not bundle `.env` automatically. Inject values via `eas.json` `build.*.env` or `npx eas-cli secret:create` so the build has them. Also ensure `.env` exists for local `npx expo start` sessions.
- **Always verify `npx eas-cli whoami` before builds.** If not logged in, `eas init` and build commands will fail with auth errors rather than prompting clearly.
